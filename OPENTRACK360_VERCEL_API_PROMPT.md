## Build the account and data platform

Bootstrap the first website administrator with a one-time operator-only process. No public signup or default admin credentials. Scope the website administrator to account management. A Circle admin manages only their own group and cannot provision platform accounts or grant platform roles. Account administration grants no map/history access.
2. Use Supabase Auth for password hashing, verification and sessions. Keep usernames as the visible identity. Implement a private, server-only unique mapping from each normalized username to an opaque internal Auth email at a controlled domain. Provision with the Auth Admin API and configure public signups off in Supabase itself. No member email or phone is required. Build provisioning so a retry or duplicate username cannot leave an orphaned account. Use a one-time display of a temporary password and an auditable admin-assisted recovery flow. Store no readable passwords. Use generic login errors and rate limits. [Supabase password authentication](https://supabase.com/docs/guides/auth/passwords) · [Admin account creation](https://supabase.com/docs/reference/javascript/auth-admin-createuser)
3. Require temporary-password rotation before access to member data. Expose the user-scoped password change via Vercel, verify the current password and test the old password and other sessions after rotation, reset and disable. Specify how outstanding sessions are invalidated and enforce it for API and database access. Protect the admin browser session with secure HTTP-only cookies, CSRF protection and server-side role checks. Keep privileged Supabase keys, push credentials and admin bootstrap material in restricted server-side environments. Limit member operations using the caller’s identity. Apply row-level security and database grants to exposed tables and Storage, including access by direct Supabase clients. Keep server-only identity mappings, token hashes and admin state private. [Supabase row-level security](https://supabase.com/docs/guides/database/postgres/row-level-security)
4. Implement the data and notification flows needed by the mobile handover matrix. Cover profiles, Circle roles and expiring invites, temporary/lightweight Circles, consent and Bubbles, live and historical points, Places, geofence and No Show rules, check-ins, Quick Notes, RSVPs, morning activity, trip progress, driving/passenger corrections, reports, Circle SOS, emergency-contact acceptance, pet profiles/routines/recovery and privacy/deletion. Keep membership and per-Circle precision checks on every map and history read. Never return precise coordinates hidden by a Bubble through a second endpoint. A Circle invitation joins an existing provisioned account. A public trip link grants only guest access. Document per-feature API ownership and unresolved dependencies from the handover.
5. Make location ingest authenticated, bounded, idempotent and safe to replay offline. Separate each user’s last valid fix from retained history. Evaluate arrival and drive-end transitions using trusted server-side rules on fresh, ordered evidence. Process the last qualifying fix and terminal state consistently before returning any newly ended location. A current session must never expose a fix captured before the share started. Use durable, duplicate-safe notification delivery, with truthful submitted, received or acknowledged states as the channel supports. Use free, supported integrations for India. For example, deliver Circle push alerts to opted-in test phones and verify the actual receipt. Keep emergency messages within the app’s configured recipients.

## Shared Android and web contract

Use `https://track.srishanth.me/api/v1` for the API. Give each share a single URL of the form `https://track.srishanth.me/s/{id}#{secret}`. The public ID routes the request. The independently generated, URL-safe random secret grants read-only access to this share. The fragment stays out of the initial HTTP request. Both viewers read it locally and send it in the Authorization bearer header to `GET /api/v1/public/shares/{id}`. A link preview, crawler or request with only the ID gets no personal data. Test that the full link survives the Android share sheet and a tap in a messaging app.

The website/API team owns `contracts/openapi.yaml` and deterministic examples under `contracts/examples/`. Both clients use those examples. Agree on these routes and units before dividing the work.

| Operation | Route or data |
| --- | --- |
| Member session | `POST /auth/login`, `POST /auth/refresh`, `POST /auth/logout`, `POST /me/password` under the API base |
| Upload fixes | `POST /locations/batch` with a unique sample ID, device capture time, latitude, longitude, horizontal accuracy in metres and nullable speed in m/s. Derive the sender from the session. |
| Manage links | `POST /shares`, `GET /shares` for the sender’s own list, `DELETE /shares/{id}` for idempotent revocation. Use authenticated `POST /shares/{id}/events` to submit arrival or drive-end evidence. Return the full secret-bearing URL only on creation. |
| Expiry policy | `mode` is `time`, `destination` or `drive_end`. A time share has `expiresAt` in UTC. An event share stays active until its specified event is confirmed or sharing is revoked. Only the destination mode requires a private destination and radius. |
| Guest view | A valid active response has `status`, `serverTime`, `viewValidUntil` and nullable `latest`. A fix contains latitude, longitude, accuracy, `capturedAt` and nullable `speedMps`. Support waiting for the first fix. Invalid credentials or an unknown link return 404. A valid ended link returns 410. Neither terminal response contains location. |

Use server time for expiry. Treat arrival, drive end, deadline and manual revocation as terminal. The first confirmed ending wins. Duplicate requests, late samples, or a reconnect must never revive a link. Use these tunable starting values in both clients’ fixtures and disclose them to senders. For arrival, require at least two fresh, sufficiently accurate fixes spanning 60 seconds inside a 150 m radius, including when a share starts at the destination. For drive end, arm the rule only after a confirmed drive and end after five continuous minutes of credible stationary evidence. A traffic light, GPS gap or parked start is insufficient. An event share whose phone has lost signal stays active, with stale data hidden, until the event can be confirmed or the sender revokes it. The custom-time mode uses the sender’s selected date/time or duration. Display the resolved local expiry or the chosen end condition before sharing.

If the sender is offline, persist a locally detected terminal event with its share ID, trusted session context and bounded evidence. On reconnect, submit and validate that event before publishing a later fix. Test a driver who arrives or parks while offline, then moves again before the connection returns. Once the server accepts the trip-ending event, those later fixes cannot be released through the old link.

A visible guest viewer refreshes about every 10 seconds under normal conditions. Each successful read grants at most 30 seconds of display time, capped at any applicable absolute deadline. Clear the marker, coordinates and speed immediately on a terminal response or when that display window lapses, including offline. On resume, validate before showing old state. Show last-fix time and visibly stale data. Withhold speed for a stale or unreliable fix. If the sender stops reporting, replace the last marker with a signal-lost state after a documented freshness limit even if the viewer can still reach the API. Display a measured zero as 0 km/h and an unknown speed as unavailable. Both viewers work signed out, require no recipient location permission and reveal only the latest fix for the shared session. Keep Circle members, historical routes, destination, identity records and contact details private.

## Build the share viewer

- At `/s/{id}`, serve a mobile-first map that also works on desktop. Show the sender’s location, current speed in km/h, accuracy, last update and waiting, stale, offline or ended states. Avoid a map pin at 0,0 during loading. Offer a normal browser experience on iPhone, desktop and Android devices without the app. Someone who opens a link should see the trip without creating an account, installing software or sharing their own position.
- Generate at least 128 bits of cryptographic randomness for the secret. Keep only its digest in the database. Resolve it to one owner and one active session. Immediately enforce revocation, deadlines and account disablement on every guest read. Exclude guest endpoints from caches, use `Cache-Control: private, no-store`, a no-referrer policy, generic social previews and no indexing. Keep tokens, coordinates and request bodies out of analytics, error reporting, URL logs and notification previews. Choose an attributed map source whose terms and free allowance cover the expected India traffic, and document any information a tile provider receives.
- Refresh from the scoped Vercel API using bounded polling. Back off in the background and on errors. A viewer that cannot refresh must clear data when its display window ends. Keep link expiry effective even if scheduled cleanup is late. Avoid publicly readable location tables or channels.
- Serve `https://track.srishanth.me/.well-known/assetlinks.json` as HTTPS 200 JSON with no redirects or login. Configure Digital Asset Links with the Android team’s actual release package and SHA-256 signing certificate fingerprint. Ensure the release manifest claims only the share path. Keep the admin and API paths outside the app’s link handling. Test Android routing with a real signed build and a tap from another app. The website must work when Android opens the URL in a browser by user choice. [Android App Links verification](https://developer.android.com/training/app-links/verify-applinks)
