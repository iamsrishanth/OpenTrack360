# Shared contract fixtures

These JSON files are deterministic, synthetic examples for Android and web clients. They describe the wire format; token strings, IDs, and Mumbai-area coordinates are test data and must never be treated as credentials or real member records.

API base: `https://track.srishanth.me/api/v1`

- Username is normalized server-side; the internal Supabase Auth email is never returned.
- Every provisioned member starts with `sharingEpoch: 1`, returned by `GET /me`. Include it at the top level of each `POST /locations/batch` request. A stale epoch returns 409 `SHARING_EPOCH_MISMATCH` and accepts no samples; discard that old queued batch. Persist the new epoch returned by `POST /me/stop-sharing` before collecting or uploading again.
- `PUT /circles/{circleId}/sharing` accepts `{ "sharingEnabled": boolean }` and changes only the caller's consent for that Circle. It does not advance the account-wide epoch or restore guest links revoked by `POST /me/stop-sharing`.
- `GET /circles/{circleId}/activity-sharing` reads the caller's persisted `{circleId,activitySharingEnabled,updatedAt}` state; `PUT` accepts `{ "activitySharingEnabled": boolean }` and changes only that caller's activity consent in the Circle.
- `POST /circles/{circleId}/invites` accepts `{clientRequestId,role?,expiresAt?,maxUses?}` and returns `{id,circleId,url,role,expiresAt,maxUses,createdAt}` once. `url` is `https://track.srishanth.me/i#{inviteToken}`; the token is only in the fragment, so it is not sent in the initial browser request. Android should open `/i` through a verified App Link when the release association is configured; browser fallback can hand off to the app. `POST /circle-invites/accept` accepts `{inviteToken}` in its authenticated JSON body after the member signs in. The server stores only a token digest; retrying the same create request ID returns a conflict because the URL cannot be recovered. See `circle-invite-create.*` and `circle-invite-accept.*`.
- `PATCH /circles/{circleId}/members/{memberId}` accepts only `{role?}` and/or `{precision?}`. Circle admins may change another member's role; a member may change only their own location precision. It cannot change another member's sharing/activity consent; use the dedicated consent routes. See `circle-member-update.*`.
- `PATCH /notifications` accepts `{notificationIds:[uuid,...]}` (1–100 unique IDs) and returns `{acknowledgedCount,acknowledgedAt}` for notifications owned by the caller. It does not reveal which submitted IDs belong to another account. See `notifications-acknowledge.*`.
- `GET /notifications` includes `circleId` and nullable `sosId`; an SOS notification uses both IDs with authenticated `GET /circles/{circleId}/sos/{sosId}` and `POST /circles/{circleId}/sos/{sosId}/acknowledge`. Notification previews never include SOS coordinates. See `notifications-list.response.json` and `sos-*.response.json`.
- Circle creation and detail return a direct `CircleSummary`; `PATCH /circles/{circleId}` currently accepts only `{name}`. Invite and member lists have dedicated list schemas; active invite listings never include the token. See `circles-create.response.json`, `circle-update.*`, `circle-invites-list.response.json`, `circle-invite-accept.*`, and `circle-members-list.response.json`.
- Place create/update responses are direct `Place` objects. Place update accepts any nonempty subset of `{name,latitude,longitude,radiusMeters,alertOnArrival,alertOnDeparture}`. Place rules use the typed `PlaceRuleInput`; responses include `placeId`, `circleId`, and server `createdAt`. See `places-*` and `place-rule-*`.
- `GET /pets/{petId}` is owner-only and returns `PetOwnerDetail`, including `recoveryFields`, `ownerMessage`, and `contactRoute` so Android can load settings before changing them. Those private settings are intentionally absent from shared `PetProfile` list entries. Create and update also return `PetOwnerDetail`. For photos, request `POST /pets/{petId}/photo` with `{contentType,sizeBytes}`, upload bytes using HTTP PUT to the returned short-lived signed `uploadUrl` with the same Content-Type and no `Authorization`/`apikey` header, then set the returned `objectPath` using `PATCH /pets/{petId}`. Do not attach the member bearer token to Storage signed URLs. The API returns short-lived signed `photoUrl` values and removes internal object paths from JSON. See `pet-detail.response.json`, `pet-create.*`, `pet-photo-upload.*` and `pet-update.*`.
- `GET /pets/{petId}/activity` returns `{data:[PetRoutineCompletionResult],nextCursor}`; lost-pet report creation returns the typed `LostPetReport`; guardian consent creation returns `{id,status:'pending',guardianUsername,createdAt}`. See `pet-activity-list.response.json`, `lost-pet-report.response.json`, and `guardian-consent.response.json`.
- Driving reports return `{data:[{tripId,memberId,startedAt,endedAt,classification,confirmedDrive}],nextCursor}`; driver/passenger correction returns `{tripId,classification,updatedAt}`. See `driving-reports-list.response.json` and `driving-classification.*`.
- Coordination wire shapes and fixtures: check-ins use `clientEventId`, `label`, device `capturedAt`, coordinates and `accuracyMeters`; Quick Notes use `clientEventId` and `text`; event creation uses `clientEventId`, `title`, `startsAt`, `inviteeMemberIds` plus nullable `endsAt`/`notes`; RSVP uses `{ "response": "yes" | "no" | "maybe" }`. See `checkins-*`, `quick-notes-*`, `events-*`, and `activity-sharing.*`.
- Morning check-ins use `clientEventId` and an optional `greeting`. Bubbles use `{ "clientEventId", "latitude", "longitude", "radiusMeters", "durationMinutes" }`, with duration up to 360 minutes; returned center coordinates are approximate. See `morning-check-in*`, `morning-check-ins-list.response.json`, and `bubbles-*`.
- Emergency contacts are existing provisioned usernames: `POST /circles/{circleId}/emergency-contacts` accepts `{ "clientRequestId": "<uuid>", "recipientUsername": "saanvi" }`; the recipient signs in and accepts by UUID at `POST /emergency-contact-invites/{inviteId}/accept`. The ID is not a bearer secret. The accepted list exposes only member ID, username and acceptance time. SOS creation and `GET /circles/{circleId}/sos/{sosId}` include per-recipient delivery/acknowledgement states. See `emergency-contact-*`, `emergency-contacts-list.response.json`, and `sos-*.response.json`.
- Trip start may include `confirmedDrive:true` only after the member explicitly confirms they are driving; the server never infers driver status from speed. The server returns `confirmedDrive` in start, list, and stop summaries so an active driver's state survives process restart; omitted or false returns false. A guest-only `POST /shares` drive-end request can also include `{ "mode": "drive_end", "confirmedDrive": true }`; this creates a private drive session with no Circle recipients if no confirmed Circle drive is active. Omitted or false never starts a standalone drive. A Circle drive can be reused for a drive-end link only from the same authenticated member session and sharing epoch that started it. Moving evidence may predate share creation only for that exact trip/session/epoch; stationary end evidence and all destination evidence must be post-share-start. Legacy active trips without recorded session and epoch must be stopped and restarted on the current device before they can be shared. A confirmed drive-end event ends the linked session and all attached drive-end guest links. Trip stop is `POST /circles/{circleId}/trips/{tripId}/stop` with `{ "clientRequestId": "<uuid>", "endReason": "arrived" | "cancelled" | "other" }`. The server supplies `endedAt`; replaying the same command does not reopen the trip. See `trip-start.*`, `trip-list.response.json`, `share-create-drive-end.*`, and `trip-stop.*`.
- `GET /shares` is sender-only and includes the stored `{latitude,longitude,radiusMeters}` destination for a destination-mode link so Android can resume local arrival monitoring after process restart. Guest responses never include that destination. See `shares-list.response.json`.
- Pet-care routines use `clientRequestId` and a typed name/kind/notes/due time/recurrence shape; completion is idempotent with `{ "clientEventId": "<uuid>" }`. See `pet-routine-*`.
- `POST /pets/{petId}/recovery-link` returns `{ "id", "url", "createdAt", "expiresAt" }` once. The URL secret appears after `#`; only its digest is stored. `DELETE /pets/{petId}/recovery-link` revokes active recovery tokens. See `pet-recovery-link*`.
- Lost-pet reports are owner-scoped to the explicit recipient Circle IDs and expire within 72 hours. `DELETE /lost-pets/{reportId}` revokes the report; replay returns the terminal result. See `lost-pet-report*`.
- Member bearer tokens are sent in `Authorization`; refresh tokens are sent in request bodies only to the refresh and logout routes.
- An administrator password reset revokes member sessions, advances the sharing epoch, disables Circle location/activity sharing, ends guest links and trips, and clears the latest location. The one-time temporary password is returned to the administrator only once; the member must rotate it and explicitly opt in to sharing again. See `admin-password-reset.response.json`.
- Platform admin operations use the secure administrator cookie; mutations also require same-origin `X-CSRF-Token`. Provisioning returns one-time temporary credentials, reset does the same while stopping all member sharing, disable reports whether the Auth ban was applied, and audit lists contain account events only. First-admin bootstrap additionally requires the server-only operator bearer secret and can succeed only once. Never use the synthetic passwords in fixtures. See `admin-provision.*`, `admin-accounts-list.response.json`, `admin-password-reset.response.json`, `admin-account-disable.response.json`, `admin-audit-list.response.json`, and `admin-bootstrap.*`.
- Guest links use `https://track.srishanth.me/s/{id}#{secret}`. The secret after `#` is read by the client and sent as `Authorization: Bearer <secret>` to `GET /public/shares/{id}`. It is never sent in a query or initial page request.
- Software-only pet recovery QR links use `https://track.srishanth.me/p/{petId}#{secret}`. The fragment secret is sent only in the `Authorization` header to the public pet recovery routes; the path ID reveals no profile data by itself.
- Speed is metres per second on the API. Convert to km/h for display (`m/s × 3.6`). A nullable speed is unknown; numeric zero is a measured stop.
- The public viewer polls about every 10 seconds. Each successful response permits at most 30 seconds of display. Clear location at `viewValidUntil`; after 90 seconds without a fresh sender fix, the API returns `signal_lost` and `latest: null`.
- Destination arrival needs two fresh, sufficiently accurate fixes at least 60 seconds apart and within 150 metres. Drive-end needs a confirmed drive and five continuous minutes of credible stationary evidence. GPS gaps, poor fixes, traffic stops, and a parked start do not end a share.
- For offline terminal events, submit `POST /shares/{shareId}/events` with the event and bounded evidence before uploading any later fix. After the server confirms a terminal event, later fixes cannot revive or update that share.
- Invalid or missing guest secrets return 404. A known ended share returns 410. Neither response includes location.
