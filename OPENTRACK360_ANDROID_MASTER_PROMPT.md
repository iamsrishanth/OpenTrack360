# Build the OpenTrack360 Android app

Act as the Android implementation lead. Build the working app, integrate it with the companion Vercel API, test it, and push the source to GitHub. Start with `LIFE360_HANDOVER.md` in the workspace and inspect the repository before choosing dependencies.

OpenTrack360 is an India-first Android app for multiple private, invitation-only groups called Circles. All included features are free to every member. Circle roles govern who can manage a group. A separate website administrator provisions accounts. Use the supplied `LIFE360_HANDOVER.md` as the inventory. Deliver the applicable software features across the full inventory. External tracking devices and networks, professional dispatch, roadside assistance, identity/credit protection, insurance and reimbursement, banking and related commercial assistance services are outside the product. Keep phone-based Circle SOS, lost-phone lookup, pet profiles and pet care. The native release is Android only. Use providers and tiers with zero project cost. If an in-scope feature has no suitable free integration in India, record the missing dependency and keep it unavailable until a free option is verified. Use original OpenTrack360 design, copy and assets.

## Deliver the member experience

1. **First sign-in.** The site administrator creates a username and temporary password on the website. The member signs in using those two fields, changes the temporary password before sharing, and can change it later with their current password in Settings. Support session refresh, logout, disabled accounts and administrator-assisted recovery. Store session secrets using Android Keystore-backed protection. An incoming guest link works even on a fresh install before sign-in.
2. **Circles and the map.** Create, invite, join, switch, leave and administer multiple private Circles. Implement expiring invites, roles, removal, temporary and lightweight Circles. Show consenting members, last update, accuracy, battery when available, activity, directions and ETA where supported. Include per-Circle sharing pause, approximate-location Bubbles, sharing indicators, controls to end a share, and a clear account-wide stop covering Circles and links. Make the effect of each control visible before it takes effect. Existing history and access after changing Circle membership need explicit, tested rules.
3. **Coordination.** Build saved Places, adjustable geofences, arrival/departure alerts, one-time and recurring No Show alerts, place suggestions, history with stops and route playback, check-ins, Quick Notes, events and RSVPs, the notification inbox, low-battery alerts, activity sharing, Morning Check In and trip progress with ETA. For No Show alerts, tell recipients when arrival could not be confirmed and why, if known. Support trip progress on the Android lock screen within the member’s privacy settings. Distinguish a confirmed arrival from a lack of data. Include the handover’s additional weather, flight and ride-coordination capabilities wherever an India-available free source can support the behavior.
4. **Driving and safety.** Detect drives, distinguish passenger trips, allow a member to correct a classification, and produce family summaries and individual reports. Report metrics the phone can actually measure. Support Circle SOS with a short cancel countdown, accepted emergency contacts and an honest delivery state. For possible-crash alerts, test privately with simulated events, provide a cancel/check-in flow, and document validation before enabling detection for members. Describe the people notified in the UI. Never claim that a responder has been dispatched.
5. **Other applicable handover features.** Include the consenting member’s lost-phone lookup, pet profiles/photos, pet-care routines, reminders and activity timeline, consent-based lost-pet reporting and software-only QR recovery where applicable. Keep lost-pet outreach within the audience the owner selects. Include permission diagnostics, privacy controls, appropriate guardian consent for any supported child accounts, account access/deletion and in-app help. Map every remaining handover item to a feature, supported integration, explicit exclusion or platform/provider dependency. Keep that matrix with acceptance evidence. Pricing tiers, real-world insurance benefits and commercial storefronts in the reference confer no OpenTrack360 entitlement.
6. **Share my live trip.** Let a sender select a custom end time or duration, choose a destination on the map, or select “When I stop driving.” Confirm exactly what the recipient sees and when the link ends. Use the Android Sharesheet and copy-link action. List active links with expiry rule, status and a prominent revoke action. Someone holding a forwarded active link can view it, so say this at creation. Allow sending to a person outside every Circle. Use an Android guest map for incoming links even when B already belongs to another Circle. Support both a cold start and an already running app.

## Shared Android and web contract

Use `https://track.srishanth.me/api/v1` for the API. Give each share a single URL of the form `https://track.srishanth.me/s/{id}#{secret}`. The public ID routes the request. The independently generated, URL-safe random secret grants read-only access to this share. The fragment stays out of the initial HTTP request. Both viewers read it locally and send it in the Authorization bearer header to `GET /api/v1/public/shares/{id}`. A link preview, crawler or request with only the ID gets no personal data. Test that the full link survives the Android share sheet and a tap in a messaging app.

The website/API team owns `contracts/openapi.yaml` and deterministic examples under `contracts/examples/`. Both clients use those examples. Agree on these routes and units before dividing the work.

| Operation | Route or data |
| --- | --- |
| Member session | `POST /auth/login`, `POST /auth/refresh`, `POST /auth/logout`, `POST /me/password` under the API base |
| Upload fixes | `POST /locations/batch` with a unique sample ID, device capture time, latitude, longitude, horizontal accuracy in metres and nullable speed in m/s. Derive the sender from the session. |
| Manage links | `POST /shares`, `GET /shares` for the sender’s own list, `DELETE /shares/{id}` for idempotent revocation. Use authenticated `POST /shares/{id}/events` to submit arrival or drive-end evidence. Return the full secret-bearing URL only on creation. |
| Expiry policy | `mode` is `time`, `destination` or `drive_end`. A time share has `expiresAt` in UTC. An event share stays active until its specified event is confirmed or sharing is revoked. Only the destination mode requires a private destination and radius. |
| Guest view | A valid active response has `status`, `serverTime`, `viewValidUntil` and nullable `latest`. A fix contains latitude, longitude, accuracy, `capturedAt` and nullable `speedMps`. Support waiting for the first fix. Invalid credentials or an unknown link return 404. A valid ended link returns 410. Neither terminal response contains location. |

Use server time for expiry. Treat arrival, drive end, deadline and manual revocation as terminal. The first confirmed ending wins. Duplicate requests, late samples, or a reconnect must never revive a link. Use these tunable starting values in both clients’ fixtures and disclose them to senders. For arrival, require at least two fresh, sufficiently accurate fixes spanning 60 seconds inside a 150 m radius, including when a share starts at the destination. For drive end, arm the rule only after a confirmed drive and end after five continuous minutes of credible stationary evidence. A traffic light, GPS gap or parked start is insufficient. An event share whose phone has lost signal stays active, with stale data hidden, until the event can be confirmed or the sender revokes it. The custom-time mode uses the sender’s selected date/time or duration. Display the resolved local expiry or the chosen end condition before sharing.

If the sender is offline, persist a locally detected terminal event with its share ID, trusted session context and bounded evidence. On reconnect, submit and validate that event before publishing a later fix. Test a driver who arrives or parks while offline, then moves again before the connection returns. Once the server accepts the trip-ending event, those later fixes cannot be released through the old link.

A visible guest viewer refreshes about every 10 seconds under normal conditions. Each successful read grants at most 30 seconds of display time, capped at any applicable absolute deadline. Clear the marker, coordinates and speed immediately on a terminal response or when that display window lapses, including offline. On resume, validate before showing old state. Show last-fix time and visibly stale data. Withhold speed for a stale or unreliable fix. If the sender stops reporting, replace the last marker with a signal-lost state after a documented freshness limit even if the viewer can still reach the API. Display a measured zero as 0 km/h and an unknown speed as unavailable. Both viewers work signed out, require no recipient location permission and reveal only the latest fix for the shared session. Keep Circle members, historical routes, destination, identity records and contact details private.

## Android tracking and links

- Request precise location, background location, activity recognition and notifications as the enabled feature needs them. Start a location foreground service from an allowed, user-visible flow, with an ongoing indicator and a stop action. Respect approximate-only and denied permissions, battery saver, OS throttling, force-stop and reboot. Show when tracking is interrupted. Opening a guest link must never start a sender service. Show the speed in km/h and local timestamps in the device’s chosen time zone.
- Sample adaptively while driving or stationary. Queue a bounded set of fixes securely offline. Validate timestamp order and accuracy. Drop stale or future fixes from live display, and prevent old uploads made after logout, revocation or a permission change from releasing private data. Scope queued samples to the signed-in identity and the consent state at capture and upload. A global stop acts locally at once, persists pending revocations while offline and accurately tells the sender when server confirmation is pending.
- Register an HTTPS Android App Link for `track.srishanth.me`, limited to `/s/`, with `android:autoVerify="true"`. Handle only that exact origin and expected link structure. Read back the production association at `https://track.srishanth.me/.well-known/assetlinks.json`. Give the Vercel team the final package ID and SHA-256 of the certificate that signs the distributed APK. Use the Play app-signing certificate if distributing through Play. Keep test signing associations on a test domain. Android or an embedded browser may honor the recipient’s browser preference. In that case the same URL must still work on the website. [Android App Links verification](https://developer.android.com/training/app-links/verify-applinks) · [Android background location](https://developer.android.com/develop/sensors-and-location/location/permissions/background)
