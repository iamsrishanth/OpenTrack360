# Android scope and acceptance map

This matrix maps the supplied `LIFE360_HANDOVER.md` inventory to OpenTrack360's India-first Android scope. Android owns the native client; the website/API team owns `apps/web/`, `supabase/`, the API implementation, and the production `assetlinks.json`. All included app features are free to Circle members. No Life360 paid-plan entitlement or commercial service is implied.

Status terms:

- **Client implemented** means Android UI and local behavior are present.
- **Contract wired** means Android sends or reads the shared API shape; it does not claim that the service is deployed or that the flow was exercised against a database.
- **Unavailable** means the client does not claim the feature until a missing route, provider, credential, or signing association exists.
- **Excluded** means the feature is outside OpenTrack360's stated product scope.

## Client security review

- Member access/refresh tokens are stored only as an AES-GCM encrypted blob in app-private storage, with a non-exportable Android Keystore key. The bounded offline location queue is also encrypted with a Keystore-backed AES-GCM key.
- The OAuth pending state, PKCE verifier, client ID, and validated API endpoints are kept as a single AES-GCM encrypted, one-use browser transaction using a separate Android Keystore key. Callback values are redacted in model diagnostics; the Activity clears the launch URI after parsing, and the app verifies the state and age before exchanging the code.
- Pet reminder schedules are encrypted with a separate Android Keystore AES-GCM key and omit user-authored names and notes. Notification text is generic and marked private for lock screens. Reminder schedules are cleared when the member signs out or changes.
- Share, pet recovery, and Circle invite fragments are parsed locally. Share/recovery public requests contain only the public resource ID and send the 32-byte URL-safe secret in `Authorization`; Circle invite acceptance sends its URL-safe token only in the authenticated JSON body after explicit account confirmation. Secret-bearing model `toString()` values are redacted, app log statements do not write request bodies or tokens, Activity URI data is cleared after routing, and parser-test failure messages redact link values.
- Sender-only destination coordinates are available to the authenticated owner for offline arrival monitoring, cached only in the encrypted, owner/session-scoped store, and redacted from model `toString()` output. The bounded offline queue remains Keystore-encrypted and fixes are scoped to capture-time consent and sharing epoch.
- Member API calls require HTTPS and disable redirects. Pet photo uploads require HTTPS to `track.srishanth.me` or a Supabase project host, use a 5 MiB limit and JPEG/PNG/WebP allowlist, and do not attach the member bearer token.
- A static scan of Android source and build configuration found no service-role keys, private-key PEM blocks, JWT bearer literals, or app-side `Log`/`println` calls. On 2026-11-28, the 46 resolved Maven coordinates in `releaseRuntimeClasspath` (including transitive runtime dependencies) were checked with the [OSV batch query API](https://google.github.io/osv.dev/post-v1-querybatch/); it returned zero vulnerability records. This is a point-in-time runtime-only scan; Gradle build plugins and test-only dependencies are not covered, and GitHub Dependabot alerts are disabled for this repository.
- The manifest disables cleartext and app backup. The production package/certificate association and Android domain verification are confirmed; actual link dispatch and user-enabled selection are not; database RLS, backend authorization, and two-member data isolation cannot be approved from the Android checkout and require the API/database review.

The production `assetlinks.json` lists the published package/fingerprint, Google's Digital Asset Links check returns `linked: true`, and Android currently reports `verified` on the emulator; the Moto last reported this on RC1 before it disconnected. Read-only path resolution matches supported routes to the release app; user link selection remains disabled, and actual implicit taps remain unverified because automatic review blocked launch. Obtain a synthetic member/share handoff before testing installed/uninstalled cold/warm implicit dispatch, real message taps, and the signed-in drive/share/guest flow. Keep synthetic routes in reports; do not place credentials, live share fragments, real location samples, or release keys in Git.
